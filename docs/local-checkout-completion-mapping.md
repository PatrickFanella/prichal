# Local completion ownership and subscription mapping

Status: implemented and locally verified on October 1, 2026. Commercial hosting entitlement remains closed.

Schema 34 extends the existing fixture binding and observation ledgers with checkout provenance. A verified binding records the original request/owner, first signed notification and worker executor. Foreign keys preserve request/organization/owner custody and signed delivery references. One original-owner `completion_bound` audit is retained per request. Each notification separately records its applied receipt. Existing qualification bindings keep their original reason and null checkout provenance.

The separately gated completion worker locks the notification, organization and original request. It matches current owner to the original actor, fixed catalog/return/authority/credential scope, confirmed customer/session IDs and saved expiry. Unrecognized references and unfinished checkpoints stay pending. Pending handover, conflicting associations and changed scope/custody refuse mapping before a provider read. Known cross-organization identity collisions are refused; a concurrent unique collision leaves work pending.

The same configured SDK client then verifies the completed session and current subscription/item/Price graph. Binding, worker audit, current observation and notification receipt commit together. Recovery checks fence event, organization and request waits, provider responses and final commit. Write failures or late holds retain no partial association or acknowledgement. An already-started read cannot be undone; snapshots still require writer quiescence.

Observations preserve explicit current checkout payment state, including unpaid. No event type, return page, completed session or subscription status grants hosting access. Later subscription-only delivery replaces the current subscription evidence and clears checkout payment state to unknown. The legacy inbox matches original checkout owner, authority/credential and Price for checkout-derived bindings, and both SDK readers share strict first-class subscription validation. No metadata/email selects ownership.
